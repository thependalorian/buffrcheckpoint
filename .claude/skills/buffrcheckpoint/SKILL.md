# Working on Buffr Checkpoint

Checkpoint replaces the paper visitor register. Its promise is that **the data protection
work is done for the customer**: the privacy notice, retention, data-request deadlines,
breach notice and evidence are built in and on from day one (blueprint section 1.5). Every
change should leave that promise truer, never weaker.

The product is called **Checkpoint** everywhere a visitor or customer sees it. The company
name appears only in contract documents, invoices and the mailbox.

## Standing rules

- **Claims (section 1.4).** Never "compliant", "certified", "guaranteed" or a hosting claim the chain does not evidence. Say what the product does. A test (`website/src/lib/copy/marketing.test.ts`) guards the public copy.
- **No hand-back disclaimers.** Do not tell the customer the work is theirs. State the legal roles once, in the Terms and Privacy Policy.
- **Schema (14.1).** A type, status or category is a `type_definition` row, never an enum or CHECK. Every stateful table gets a status log in the same migration. No triggers, no cascades, soft deletes, tenant column first in every index, UUIDs generated by the client. A new table is a proposal until the owner signs it off.
- **Engineering (34).** Real database, server-side validation, tenant scope, audit events, tests. Parameterised queries only. The project logger, never raw `console`. No emojis in code, comments or docs. Exact dependency versions and a 7-day cool-down on new packages. Fail closed on secrets in production.
- **Fix in the same pass.** A defect found while working is fixed, tested and documented. It stays open only if it needs the owner's decision, a credential only they hold, real data you do not have, or core-schema design reserved to a human. Say which.
- **Update the blueprint** after every change that alters behaviour, a rule or a decision. Summaries extend `buffrcheckpoint.md` or `docs/`; never a new dated report file.
- **Secrets are never printed.** Read names and lengths only. Set values from stdin.
- **Subagents only when asked.** Do research and audits in the main thread.

## Workflows

### Change a feature

```
- [ ] 1. Read the blueprint section and the code it names; grep for the existing helper before writing a new one
- [ ] 2. Implement with the real database path and the audit event; copy goes to lib/copy
- [ ] 3. Tests: unit next to the code; for a public route add an HTTP-level test (see backend/src/modules/kyb/kyb.controller.spec.ts)
- [ ] 4. tsc, lint (biome check on touched files only), full suites (scripts/run-all-tests.sh), route audit
- [ ] 5. Update buffrcheckpoint.md (section, decision log, owner decisions)
- [ ] 6. Commit; deploy only what changed; verify live
```

### Migration

1. Write `backend/db/migrations/00NN_name.sql`: `BEGIN; ... COMMIT;`, `IF NOT EXISTS`, `INSERT ... WHERE NOT EXISTS`. Guard role grants with a `pg_roles` check. Append-only logs: `REVOKE UPDATE, DELETE` for `buffr_checkpoint_runtime`.
2. Add the matching Drizzle columns. If a template row is seeded, add the migration to the seed list in `template-catalog.spec.ts`.
3. Apply to the `dev-local` Neon branch **twice**; check counts. Never delete Neon branches without asking (the branch limit is real).
4. Apply to production with the owner role, twice, then check privileges (`has_table_privilege` on `audit_events`: UPDATE false, DELETE false, INSERT true).
5. Deploy the API, then the web apps.

### Deploy

- API: `railway up --service api --detach` from `backend/`; wait for `SUCCESS`; read the start-up log (document reader line, worker modes). Railway builds with **Railpack**; OS packages go in `backend/railpack.json`.
- Web apps: `vercel --prod --yes` from `website/`, `admin/`, `ops-console/`. `NEXT_PUBLIC_*` values are baked in at build, so set them first, then deploy.
- Order when a frontend sends something the API now requires: frontends first, API second.
- Verify: `/health`, `scripts/smoke-production.sh`, a status check of the pages you changed.

### Business verification, email, secrets

- KYB end to end: `backend/scripts/kyb-pipeline-check.ts` on a development database with a real filing. Required pack and decisions are in blueprint 7.5 and D-37, D-38.
- Branded mail through the real pipeline: `backend/scripts/send-test-email.ts` (development database, disables the retention and report workers by variable).
- Secrets: `printf '%s' "$VALUE" | railway variable set NAME --stdin --service api --skip-deploys`; Vercel `vercel env add NAME production --no-sensitive` for public values.

### Production checks that need the owner

Additive migrations and deploys of finished, tested work are routine. These need the owner first: a new table (schema sign-off), switching retention mode, a new subprocessor or provider, changing the legal entity or Terms wording, anything that deletes data, and any write to production data outside a migration.
